# Decisions

## DEC-001: Каждый проект начинается с Discovery

- Дата: 2026-07-20
- Статус: Accepted
- Решение: каждый новый проект начинается с этапа Discovery / Опрос и сбор информации.
- Причина: до проектирования, выбора стека и разработки нужно собрать цели, аудиторию, ограничения, критерии успеха и референсы.
- Последствия: переход к Requirements возможен только после принятия результата Discovery заказчиком.

## DEC-002: Stage Gate между SDLC-этапами

- Дата: 2026-07-20
- Статус: Accepted
- Решение: после завершения каждого SDLC-этапа Codex показывает результат, фиксирует ключевые изменения и запрашивает принятие этапа.
- Причина: не переходить к следующему этапу автоматически и сохранять управляемость проекта.
- Последствия: Requirements, Design, Environment Setup, Development, Testing, Deployment и Maintenance начинаются только после явного подтверждения.

## DEC-003: Базовые документы проекта

- Дата: 2026-07-20
- Статус: Accepted
- Решение: в каждом новом проекте создаются `docs/DISCOVERY.md`, `docs/PROJECT_PLAN.md`, `docs/DECISIONS.md`, `docs/PROJECT_LOG.md`.
- Причина: нужен понятный источник правды по вводным, плану, решениям и ходу проекта.
- Последствия: ключевые изменения внутри этапов фиксируются в документах проекта.

## DEC-004: Git-инструмент

- Дата: 2026-07-20
- Статус: Accepted, выполнено в DEC-048
- Решение: ориентироваться на Git for Windows для командной работы с репозиторием.
- Причина: GitHub Desktop удобен визуально, но Codex нужен `git.exe` в командной строке для веток, коммитов и push.
- Последствия: Git for Windows должен быть установлен вручную или после отдельного разрешения; фактическая установка зафиксирована в `DEC-048`.

## DEC-005: Размещение

- Дата: 2026-07-20
- Статус: Accepted
- Решение: целевой веб-ресурс для публикации игры - Netlify.
- Причина: Netlify подходит для статического фронтенда, serverless-функций и публичного доступа по ссылке.
- Последствия: в проекте планируются Netlify Functions, Netlify Blobs и последующая настройка деплоя.

## DEC-006: Идентификация игрока в таблице рекордов

- Дата: 2026-07-20
- Статус: Accepted
- Решение: таблица рекордов использует анонимный локальный `playerId`.
- Причина: имя игрока не является надежным уникальным идентификатором; два игрока могут выбрать одно имя, а один игрок может изменить имя.
- Последствия: при первом запуске браузер создает `playerId` и сохраняет его в `localStorage`; API рекордов принимает `{ playerId, name, score }`; имя используется как отображаемое имя.
- Ограничение: при смене браузера, устройства или очистке данных сайта игрок будет считаться новым игроком; аккаунты в v1 не добавляются.

## DEC-007: Изменение отображаемого имени

- Дата: 2026-07-20
- Статус: Accepted
- Решение: игрок может менять отображаемое имя при новом запуске или на экране окончания игры.
- Причина: имя является публичной подписью в таблице рекордов, а не уникальным идентификатором.
- Последствия: исходное правило было заменено решением `DEC-063`; теперь новое имя на том же устройстве создает отдельный локальный профиль и отдельный `playerId`.

## DEC-008: Ограничения v1

- Дата: 2026-07-20
- Статус: Accepted
- Решение: в v1 не включать аккаунты, авторизацию, мультиплеер, магазин, платежи, сложные уровни, админ-панель, аналитику игроков и синхронизацию игрока между устройствами.
- Причина: первая публичная версия должна быть легкой, быстро проверяемой и сфокусированной на игровом сценарии.
- Последствия: v1 включает управление, учет очков, жизни, игровой сценарий и таблицу рекордов без усложнений.

## DEC-009: Длительность игровой попытки

- Дата: 2026-07-20
- Статус: Accepted
- Решение: длительность игровой попытки определяется тем, на сколько игроку хватит жизней.
- Причина: механика игры строится на росте сложности, а не на фиксированном таймере.
- Последствия: скорость и частота падения предметов должны увеличиваться по мере игры; баланс роста сложности прорабатывается на Design.

## DEC-010: Машинный бонусный сценарий

- Дата: 2026-07-20
- Статус: Accepted for Design
- Решение: сценарий со сбором машины из запчастей вынести в Design как отдельную бонусную механику.
- Причина: механика интересная, но требует балансировки длительности, условий активации и влияния на скорость.
- Последствия: для v1 будет рассмотрен вариант, где сбор запчастей включает режим "машина" со скоростью x2 на ограниченное время.

## DEC-011: Стартовые жизни

- Дата: 2026-07-21
- Статус: Accepted
- Решение: игрок начинает попытку с 3 жизнями.
- Причина: это простой и понятный стандарт для аркадной игры.
- Последствия: игра заканчивается после потери всех 3 жизней.

## DEC-012: Старт игры

- Дата: 2026-07-21
- Статус: Accepted
- Решение: отдельный стартовый экран не нужен; игра начинается по кнопке "Старт" на основном игровом экране.
- Причина: первая версия должна быстро запускать игрока в действие.
- Последствия: основной экран должен содержать игровое поле, HUD и кнопку "Старт".

## DEC-013: Запчасти машины

- Дата: 2026-07-21
- Статус: Accepted
- Решение: запчасти машины не дают очки напрямую, а собирают бонус.
- Причина: машинная механика должна ощущаться отдельной наградой, а не обычным типом очков.
- Последствия: детали бонуса прорабатываются отдельно в `docs/MACHINE_BONUS_SCENARIO.md`.

## DEC-014: Рост сложности

- Дата: 2026-07-21
- Статус: Accepted
- Решение: первичная модель предполагала смешанный рост сложности - по времени и по очкам; актуальная runtime-модель позднее уточнена в `DEC-059`.
- Решение: первичный шаг был +1 уровень каждые 60 секунд и +1 уровень за каждые 200000 очков; актуальная модель позднее уточнена в `DEC-061`.
- Решение: первоначально скорость падения росла с 100% до 190%, частота появления предметов - с 100% до 220%; runtime-баланс v1 позднее уточнен в `DEC-053`.
- Решение: доля вредных предметов растет с 6% до 15%; первичная пропорция внутри вредных была 65% налог / 35% штраф, актуальная runtime-пропорция уточнена в `DEC-055`.
- Решение: доля договора растет с 2% до 5%; после появления договора следующий договор не может появиться раньше чем через 8 секунд; если договор не появлялся 30 секунд, его шанс временно повышается.
- Решение: первичное ограничение роста не чаще 1 уровня за 10 секунд позднее заменено актуальной моделью из `DEC-059`.
- Причина: игра должна постепенно ускоряться сама, а успешный игрок должен быстрее выходить на более азартный темп без резких скачков сложности.
- Последствия: детальные параметры зафиксированы в `docs/DIFFICULTY_BALANCE.md`; вероятности купюр, мебели, запчастей и бензина уточняются отдельно.

## DEC-015: Порядок фиксации предложений Codex

## DEC-016: Очки и вредные предметы

- Дата: 2026-07-21
- Статус: Accepted
- Решение: в v1 используются согласованные правила очков: купюры 500/1000/5000 дают очки по номиналу; зеркало +10000; прихожая +20000; кухня +50000; договор +100000; запчасти и бензин очки не дают.
- Решение: купюры 100 и 200 исключены из v1.
- Решение: налог снимает 50000 очков, но счет не падает ниже 0; штраф снимает 1 жизнь; пропущенный договор снимает 1 жизнь.
- Причина: договор должен быть самым ценным обычным бонусом, мебель - крупной ценностью, а вредные предметы должны иметь понятные разные последствия.
- Последствия: точные вероятности выпадения предметов нужно утвердить отдельно.

## DEC-017: Бензин и продолжительность машинного бонуса

- Дата: 2026-07-21
- Статус: Accepted
- Решение: бензин падает отдельным предметом в виде канистры на 20 литров.
- Решение: канистра добавляет +20 литров бензина; 1 литр бензина равен 1 секунде движения на машине.
- Решение: прежнее правило фиксированной продолжительности машины отменено; длительность бонуса зависит от собранного бензина.
- Причина: игрок должен видеть понятный ресурс, который управляет временем действия бонуса.
- Последствия: в интерфейсе нужно показывать запас бензина рядом с индикатором машины.

## DEC-018: Состав машины

- Дата: 2026-07-21
- Статус: Accepted
- Решение: для запуска машинного бонуса нужно собрать 4 колеса, двигатель и корпус.
- Решение: корпус машины - желтая Mazda Atenza 2002 года; для реализации и визуального брифа использовать формулировку "желтый седан 2002 года в стиле Mazda Atenza, без логотипов".
- Решение: запчасти собираются в любом порядке; до полной сборки игра по возможности роняет только недостающие детали.
- Решение: дубль уже собранной детали не дает очки, не ломает сборку и показывает короткую смешную реакцию "лишняя деталь".
- Причина: игроку нужен визуально понятный прогресс сборки машины.
- Последствия: на экране нужно отображать слоты колес, двигателя, корпуса и количество бензина.

## DEC-019: Визуальная роль героини и кошелька

- Дата: 2026-07-21
- Статус: Accepted
- Решение: на основном игровом экране главная героиня отображается в деловом костюме с большим кошельком, куда попадают пойманные предметы.
- Решение: при активном машинном бонусе отображается желтый седан 2002 года в стиле Mazda Atenza, без логотипов; из седана должна быть видна главная героиня в деловом костюме с большим кошельком.
- Решение: даже в режиме машины предметы визуально попадают в большой кошелек героини.
- Причина: героиня и кошелек являются главным визуальным образом игры и должны сохраняться во всех режимах.
- Последствия: фото героини будет предоставлено заказчиком позже и использовано как визуальный референс на этапе Design.

## DEC-020: Правила машинного бонуса

- Дата: 2026-07-21
- Статус: Accepted
- Решение: машина активируется, когда собраны все детали и есть бензин.
- Решение: если машина собрана, но бензина нет, в HUD показывается состояние "Нужен бензин"; машина ждет канистру.
- Решение: во время активного режима "машина" новые запчасти не падают.
- Решение: во время активного режима "машина" канистры бензина могут падать и добавлять бензин до максимума 60 литров.
- Решение: машина не защищает от налога и штрафа.
- Решение: пропущенный договор снимает 1 жизнь даже в режиме "машина".
- Причина: машинный бонус должен давать сильное ускорение, но не превращать игрока в неуязвимого.
- Последствия: оставшийся открытый вопрос - вероятности выпадения запчастей машины.

## DEC-021: Частота выпадения бензина

- Дата: 2026-07-21
- Статус: Accepted, уточнено в DEC-041
- Решение: максимум бензина - 60 литров.
- Решение: 60 литров бензина дают 60 секунд запаса движения при полном баке.
- Решение: 3 канистры по 20 литров дают максимальный запас: 60 литров = 60 секунд.
- Решение: шанс канистры среди всех предметов зависит от состояния машины и запаса бензина.
- Частоты:
  - машина не собрана: 2%;
  - машина не собрана, бензина 60 л: 0%;
  - машина собрана, бензина 0: 4%;
  - машина активна, бензина 1-20 л: 3%;
  - машина активна, бензина 21-40 л: 2%;
  - машина активна, бензина 41-60 л: 1%.
- Решение: актуальная runtime-шкала позднее уточнена в `DEC-056`.
- Причина: бензин должен быть важным ресурсом, но не должен делать бонус бесконечным.
- Последствия: канистра остается способом заранее накопить ресурс и продлить активный режим машины.

## DEC-022: Вероятности выпадения предметов

- Дата: 2026-07-21
- Статус: Accepted
- Решение: согласована модель выпадения предметов по категориям: договор, вредный предмет, бензин, запчасть машины, обычный полезный предмет.
- Решение: запчасти машины выпадают с шансом 10-14%, пока машина не собрана; если машина собрана или активна, шанс запчастей 0%.
- Решение: шанс запчастей зависит от уровня сложности: уровни 1-3 - 10%, уровни 4-6 - 12%, уровни 7-10 - 14%.
- Решение: среди недостающих деталей веса такие: колесо 50%, двигатель 25%, корпус 25%.
- Решение: внутри купюр распределение: 500 - 60%, 1000 - 30%, 5000 - 10%.
- Решение: внутри мебели распределение: зеркало - 50%, прихожая - 35%, кухня - 15%.
- Причина: модель дает частые маленькие награды, редкие крупные бонусы, понятный прогресс машины и контролируемую долю риска.
- Последствия: детальная модель зафиксирована в `docs/ITEM_SPAWN_PROBABILITIES.md`.

## DEC-023: Структура основного экрана и HUD

- Дата: 2026-07-21
- Статус: Accepted
- Решение: использовать фон `tomsk-collage-desktop.png` для desktop и `tomsk-collage-mobile.png` для mobile.
- Решение: на desktop счет размещается сверху слева; строка ниже счета содержит жизни, паузу, рестарт и кнопку рекордов; HUD машины размещается сверху справа.
- Решение: на mobile верхняя строка содержит очки и жизни, вторая компактная строка содержит машину и бензин, а пауза, рестарт и рекорды доступны иконками в правом верхнем углу.
- Решение: таблица рекордов открывается как модальное окно поверх игры; Game Over показывает счет, ввод имени, сохранение результата и топ-10.
- Решение: HUD машины показывает 4 колеса, двигатель, корпус и бензин; пустой слот - серый контур, собранная деталь - цветная иконка именно этой детали.
- Решение: если машина собрана, но бензина нет, показывается статус `Нужен бензин`; если машина активна, индикатор подсвечен, бензин убывает.
- Причина: такая структура сохраняет читаемость игры, не закрывает фон и разделяет обычный игровой статус и бонусную механику.
- Последствия: детали экранов зафиксированы в `docs/SCREEN_FLOW.md`; визуальные требования HUD зафиксированы в `docs/VISUAL_BRIEF.md`.

## DEC-024: Игровой цикл и hitbox-логика

- Дата: 2026-07-21
- Статус: Accepted
- Решение: игровой цикл работает через `requestAnimationFrame`.
- Решение: состояния игры: `idle`, `playing`, `paused`, `carMode`, `gameOver`, `leaderboard`.
- Решение: ловля считается по пересечению hitbox предмета с hitbox большого кошелька; ловит кошелек, а не вся героиня.
- Решение: hitbox кошелька примерно на 10-15% больше видимого кошелька; в режиме машины hitbox остается у кошелька.
- Решение: предмет считается пропущенным, когда полностью ушел ниже нижней границы игрового поля.
- Решение: первоначальная модель пропусков позднее уточнена в `DEC-054`: купюры не влияют на счетчик пропусков, мебель/детали/бензин влияют.
- Решение: пауза и таблица рекордов замораживают движение, таймеры, бензин и рост сложности.
- Решение: `gameOver` наступает при 0 жизней и показывает итоговый счет, имя, сохранение результата, топ-10 и кнопку повтора.
- Решение: первоначальная модель неуязвимости позднее уточнена в `DEC-053`: после потери жизни действует защита `700 мс` от повторного мгновенного списания жизни.
- Причина: модель простая, понятная и хорошо подходит для Canvas 2D.
- Последствия: подробности зафиксированы в `docs/GAME_LOOP_DESIGN.md`.

## DEC-025: Визуальный бриф

- Дата: 2026-07-21
- Статус: Accepted
- Решение: визуальное направление v1 - яркая рисованная 2D arcade игра, дружелюбная, легкая и с юмором.
- Решение: уровень карикатурности героини - средний; фото используется как референс, но не как фотореалистичная вставка.

- Решение: мебель намеренно разных цветов и стилей, чтобы поддерживать юмор.

- Решение: HUD компактный, без тяжелых карточек.
- Причина: стиль должен сочетать референс героини, яркий Томск-фон и аркадную читаемость.
- Последствия: подробный визуальный бриф зафиксирован в `docs/VISUAL_BRIEF.md`; следующий шаг - prompts для ассетов.

## DEC-026: Prompt pack для ассетов

- Дата: 2026-07-21

## DEC-031: API-контракт таблицы рекордов

- Дата: 2026-07-21
- Статус: Accepted
- Решение: для v1 используется API на Netlify Functions и хранение рекордов в Netlify Blobs.
- Решение: API содержит `GET /.netlify/functions/scores` для получения top-10 и `POST /.netlify/functions/scores` для сохранения результата.
- Решение: `playerId` создается в браузере через `crypto.randomUUID()` и хранится в `localStorage`.
- Решение: публичный ответ API не возвращает raw `playerId`; текущий игрок отмечается флагом `isCurrentPlayer`.
- Решение: для одного `playerId` хранится только лучший результат; более низкий результат не обновляет `score`, но может обновить отображаемое имя.
- Решение: имя игрока ограничено 20 символами и допускает кириллицу, латиницу, цифры, пробел, дефис и underscore.
- Решение: top-10 сортируется по `score desc`; при равенстве очков выше тот, кто набрал результат раньше.
- Решение: frontend хранит pending-result в `localStorage`, если API временно недоступен.
- Причина: такой API закрывает требования v1, сохраняет простую идентификацию игрока и подходит для Netlify-размещения.
- Последствия: подробный контракт зафиксирован в `docs/API_CONTRACT.md`.

- Решение: на уровне 40 игра генерирует примерно `92` предмета в минуту.
- Решение: доля вредных предметов масштабируется от `6%` до `22%`; внутри вредных сохраняется пропорция `Налог 70% / Штраф 30%`.
- Решение: доля договора масштабируется от `2%` до `5%`.
- Решение: шанс бензина изменен: машина не собрана и бензина меньше 60 л - `3%`; машина собрана и бензина 0 л - `6%`; `Car Mode` 1-10 л - `8%`; 11-20 л - `6%`; 21-40 л - `4%`; 41-60 л - `2%`.
- Решение: `Pity Timer` бензина изменен с `12` на `15 секунд`.
- Решение: канистра бензина продолжает падать на `15%` медленнее обычных легких предметов.
- Решение: детали автомобиля стали редкой категорией: уровни 1-10 - `4%`, 11-20 - `5%`, 21-30 - `6%`, 31-40 - `7%`.
- Решение: между появлением деталей автомобиля выдерживается минимальная задержка `8 секунд`.
- Причина: игра должна развиваться плавнее и дольше, а машина должна быть долгосрочной бонусной целью, а не слишком быстрым ранним усилением.
- Последствия: предыдущее runtime-решение `DEC-061` считается устаревшим для текущей реализации; актуальные правила описаны в `docs/DIFFICULTY_BALANCE.md`, `docs/ITEM_SPAWN_PROBABILITIES.md` и `docs/MACHINE_BONUS_SCENARIO.md`.
